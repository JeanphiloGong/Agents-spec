# Prompt Architecture Review

## Overview

Review prompts as executable task specifications. This skill does not ask
"does the prompt sound good?" It checks whether the prompt gives the model the
right task model, input schema, decision path, few-shot boundaries, and output
contract to behave reliably.

Lead with findings. Approve only when the prompt is structurally usable for the
stated task.

## When to Use

- A prompt generated by `prompt-architecture-author` needs independent review.
- A prompt fails on OCR noise, candidate conflicts, incorrect rejection,
  over-binding, under-binding, or schema confusion.
- A production prompt is mostly rules or negative constraints.
- A team needs to decide whether a prompt is ready for evaluation or rollout.
- A prompt has changed and must be reviewed before replacing an existing
  version.

**When NOT to use:** casual chat prompt polishing, purely stylistic rewriting,
model benchmark design, jailbreak analysis, or API integration debugging.

## The Review Loop

1. Establish the Contract
   - Identify the intended task family and output consumer.
   - Identify the supplied input objects and expected output.
   - Verify: the review is judging the prompt against the real task, not an
     imagined generic prompt standard.
2. Check Task Model Fit
   - Does the role explain what decision the model owns?
   - Does it separate the task from adjacent tasks such as extraction, recall,
     search, summarization, or entity recognition?
   - Does it state what the model should optimize for?
3. Check Input Schema
   - Are all top-level inputs defined?
   - Are candidate objects and IDs defined if selection is required?
   - Are noisy, optional, derived, or unreliable fields labeled?
   - Could a model know what it may return without inferring hidden structure?
4. Check Decision Process
   - Is there a numbered process?
   - Does it follow the model's cognition path from task type to evidence to
     conflict handling to final output?
   - Are uncertainty, conflict, and rejection handled before output?
5. Check Rules and Policy
   - Are hard rules minimal and non-duplicative?
   - Are repeated rules wasting attention?
   - Are negative constraints balanced by a positive decision path?
6. Check Few-Shots
   - Does the prompt include a common positive path?
   - Does it include noisy-input tolerance when needed?
   - Does it include explicit conflict and reject examples?
   - Do examples use the same input and output schema as the real prompt?
7. Check Output Contract
   - Is the response parseable?
   - Are allowed values and empty/null behavior explicit?
   - Are returned IDs constrained to input candidates?
   - Are reason/confidence fields justified by caller needs?
8. Return Verdict
   - Use `pass`, `revise`, or `block`.
   - `pass` only if the prompt can move to evaluation or rollout.
   - `revise` when fixes are clear and local.
   - `block` when task model, schema, or output contract is too ambiguous to
     trust.

## Decision Points

- If the prompt lacks input schema, default to `block` for candidate-selection
  or structured-output tasks.
- If the prompt has schema and process but weak examples, default to `revise`.
- If the prompt repeats rules but remains unambiguous, ask for simplification
  rather than blocking.
- If the prompt asks for hidden chain-of-thought in output, require a safer
  rationale or reason field.
- If the prompt contains real private data in examples, block until examples
  are anonymized or synthetic.

## Common Rationalizations

| Rationalization | Reality |
|---|---|
| "The prompt has many rules, so it is robust." | Robust prompts have task model, schema, process, examples, and output contract. |
| "The examples are nice-to-have." | For noisy or ambiguous tasks, examples define the boundary behavior. |
| "The schema is obvious from the code." | The prompt must stand alone for the model at inference time. |
| "It only fails sometimes." | Intermittent failures often mean missing conflict, reject, or noisy-input guidance. |
| "A stronger system role will fix it." | Role helps only after the task and input are structurally clear. |

## Red Flags

- The prompt starts with policy and never defines the task model.
- The role could apply to many unrelated tasks.
- The prompt says "choose from candidates" but never defines candidate shape.
- The decision flow is hidden inside unordered rules.
- Few-shots use a different schema from real inputs.
- There is no reject or empty-output example for a task that can reject.
- Rules repeat across multiple sections.
- The output schema allows values not grounded in input.
- The prompt relies on hidden reasoning or private context.

## Verification

- [ ] Task family and non-task are clear.
- [ ] Input schema is complete enough for inference.
- [ ] Decision process is explicit and ordered.
- [ ] Hard rules are minimal and not repeated.
- [ ] Few-shots cover common, noisy, conflict, and reject behavior when
      relevant.
- [ ] Output schema is parseable and grounded in the input.
- [ ] No secrets, private examples, invented tools, or unsupported capabilities
      are present.
- [ ] Verdict is backed by concrete findings.

## Output Format

```text
## Verdict
- pass | revise | block

## Findings
- [severity] [section] Finding with concrete evidence.

## Missing Examples
- ...

## Schema Issues
- ...

## Rule and Policy Issues
- ...

## Recommended Fix
- ...
```

## Guardrails

- Lead with findings, not praise.
- Do not rewrite the whole prompt unless the user asks for a rewrite.
- Do not approve a candidate-selection prompt without candidate schema.
- Do not approve a structured-output prompt with ambiguous empty/null behavior.
- Do not treat more rules as a substitute for few-shots.
- Do not require examples irrelevant to the task family; review against the
  actual task.
